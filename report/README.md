## ⚠ 关于 `docs/` 里的 Python 引用

`docs/` 是本工程的**过程文档**，记录的是**完整项目**（PL + PS + 主机侧）
在开发过程中发生的事。所以它们会提到一些 Python 路径
（PC 侧 golden 参考实现、板上驱动、数据转换脚本等）。

**那些 Python 不在本交付目录内** —— 见根 `README.md`「本目录范围」。
文档保留原文是为了**如实记录当时的排查过程**（改了反而失真）。

**如果你要复现某个操作而找不到对应的脚本，那是预期的** ——
那些脚本由其它人维护。

## 决策记录为什么值得单列

本报告按赛题要求「**将设计过程中的判断依据写进报告，而不只是呈现结果**」
组织。几条典型：

| 决策 | 依据 |
|---|---|
| 几何处理放最前 | 昂贵算子只在小图上跑，**算力差 33 倍** |
| CNN 放 PS 不放 PL | 异构划分沿**「数据量 × 操作次数」**切（不是"PL 做不到"） |
| 分区用 Verilog 还是 HLS | 需精确控制时钟域/边沿的走 RTL，计算密集走 HLS |
| 阈值叫"全图均值"不叫"自适应" | 是**整幅一个阈值**，不是分块 —— 对外表述必须准确 |
| `use_ila=0` | 开着会让 BRAM 涨到 52.5% 并引入 **WHS −1.830 ns** 跨异步域违例 |

## 报告里最值得看的一节

`design.md` §4.5「时序瓶颈定位」—— **查出瓶颈根本不在本设计里**：

> 全设计 10 条最差 setup 路径**全部属于 AMD `v_tc` IP 内部**
> （一条布线 9.1 ns、逻辑仅 0.64 ns、扇出 433 的网）。
> 改我们的 RTL / HLS 对它**零影响**。

这条决定了"要不要为时序余量做优化"这个问题的答案 —— 而它是**查出来的**，
不是猜的。
